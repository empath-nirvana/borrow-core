# Interior mutability: how Rust uses it, and what we do instead

The language has no `Cell`, `RefCell` or `Rc<RefCell>`. `Imm` borrows are deeply immutable in
the model: the relation's `Imm` clause makes a lent cell an `imm` cell, and the frame results
depend on that (`experiments/FrameTheorems`: `imm_call_keeps`, `wpTS_footprint`). This
experiment asks two questions. What do real Rust programs use interior mutability for? And what
does each use cost here, today and with the features that are planned?

It has four parts:

- a survey of crates.io source (`survey/`);
- eight small Rust programs, one per category (`rs/`);
- eleven borrow-core programs that run and compute the same answers (`bc/`);
- four sketches of features that are not built (`sketches/`).

Nothing here is imported by the library. No Lean code was added, and no file outside this
directory was changed except the row in `experiments/README.md`.

    experiments/InteriorMutability/run.sh           run every bc/*.bc (compiled and interpreted)
                                                    and every rs/*.rs, and compare with the goldens
    experiments/InteriorMutability/run.sh --write   rewrite the goldens and bc/counts.txt

These programs are not wired into `scripts/ci-local.sh`, since `corpus/` and
`corpus/counts.expected` were off limits. `run.sh` performs the same checks as
`compile-corpus.sh`: `bcc run` must equal `bcc interp`, the heap must end empty (`live 0`), and
the allocation and dispatch counts must match.

## 1. The survey

### Method

The census and the sample were produced with the scripts in `survey/`.

- **Corpora.** The local `~/.cargo/registry` holds only 26 crates, too few to generalise from.
  Two corpora were therefore downloaded from crates.io (`survey/fetch.sh`, crate lists with
  versions in `survey/meta/`):
  - the **top 500 crates by all-time downloads**;
  - **151 application-level crates**: the most-downloaded in the `gui`, `game-development`,
    `wasm` and `compilers` categories, excluding any already in the top 500.

  The toolchain's `std` sources (rustc 1.97.1) were scanned as well.
- **Census.** `survey/census.py` runs lexical regexes over `.rs` files and skips line comments.
  `survey/tl.py` counts how many cells are declared inside `thread_local!` blocks.
- **Sample.** `survey/sample.py`, with seed `20260928`, takes one random hit per crate and then a
  random subset of crates: 50 `RefCell<` sites and 40 `Cell<` sites, 90 in all. Every site was
  read in context and assigned one primary category
  (`survey/meta/sample-classified.tsv`, generated by `survey/meta/classify.py`).
- **Web.** The Rust Book, the `std::cell` documentation, blog posts, forum threads and published
  studies, all cited below.

**Limits of the method.**

- One reader classified the sample, with one category per site.
- With n = 90, the counts establish rank order, not precise shares.
- The regexes count type mentions, not constructions.
- The top 500 leans towards infrastructure, proc-macro and `-sys` crates. Application binaries
  are not on crates.io, so they are absent from both corpora.
- GitHub code search was not used: the API requires authentication.
- No published study of `RefCell` usage frequency turned up. That does not prove none exists.

**Verdict on the proposed categories.**

- **Caches and mocks** are confirmed as the largest.
- **The Rust Book's two examples** are a `MockMessenger` and an `Rc<RefCell>` list. The mock
  matches a large category; the `Rc<RefCell>` list does not. Shared-ownership graphs are 4/90,
  and outside GUI crates they are rare.
- **`Fn` vs `FnMut` and graph algorithms** are 1/90 each.
- **Lazy init.** In library code, `Cell` for lazy init appears mostly *inside* the implementations
  of lazy primitives (spin, tracing-core, lazy_static, once_cell). Application code uses
  `OnceCell` or `LazyLock` directly.
- **Thread-local** is a scope, not a purpose. Its purpose is almost always ambient context.
- **New categories.** Three were split out that the proposed list did not have: accumulators
  (9b), markers (9c) and arena annotations (9d).

### What the literature and guides say

- **The `std::cell` documentation** calls interior mutability "something of a last resort". It
  lists three cases: mutability inside `Rc`/`Arc`, implementation details of logically-immutable
  methods (caching), and mutating `Clone` impls (<https://doc.rust-lang.org/std/cell/>).
- **The Rust Book** ch15-05 gives the two examples above
  (<https://doc.rust-lang.org/book/ch15-05-interior-mutability.html>).
- **Arenas are the standard advice** for graphs:
  - Niko Matsakis, "Modeling graphs in Rust using vector indices"
    (<https://smallcultfollowing.com/babysteps/blog/2015/04/06/modeling-graphs-in-rust-using-vector-indices/>);
  - Manish Goregaokar, "Arenas in Rust"
    (<https://manishearth.github.io/blog/2021/03/15/arenas-in-rust/>);
  - indextree, which advertises "no RefCell" (<https://github.com/saschagrunert/indextree>);
  - Too Many Lists, whose doubly-linked chapter is "a demonstration that this is a very bad idea"
    (<https://rust-unofficial.github.io/too-many-lists/fourth.html>).
- **UI frameworks.**
  - Leptos signals are `Copy` arena indices (<https://book.leptos.dev/appendix_life_cycle.html>).
    The Dioxus `Signal` is described as a `Copy` `Rc<RefCell<T>>` for UIs. Both descriptions come
    from search summaries; those pages were not read.
  - gtk-rs requires `'static` `Fn` signal handlers, hence `Rc<Cell>`
    (<https://gtk-rs.org/gtk4-rs/stable/latest/book/g_object_memory_management.html>).
  - wasm-bindgen's requestAnimationFrame example keeps its self-referencing closure in
    `Rc<RefCell<Option<_>>>`.
- **Studies.**
  - Qin et al., PLDI 2020: `RefCell` borrow panics are the root cause of 4 of 38 non-blocking
    concurrency bugs, and the paper recommends restricting interior mutability
    (<https://cseweb.ucsd.edu/~yiying/RustStudy-PLDI20.pdf>).
  - Astrauskas et al., OOPSLA 2020 and Zhu et al., ICSE 2022 give no `RefCell` usage figures.

## 2. The programs

Each `rs/*.rs` is idiomatic Rust using interior mutability. It compiles with rustc 1.97.1 and
prints its answer, recorded in `rs/*.out`. Each `bc/*.bc` computes the same answer in core
syntax plus the sugar `bcc` accepts on `main`. Each one is run compiled and interpreted, ends
with `live 0`, and is recorded in `bc/*.out`, with its counts in `bc/counts.txt`. Lines are
non-blank, non-comment lines.

| program | Rust | borrow-core | lines rs → bc | runs | allocs / dispatched | API change |
|---|---|---|---|---|---|---|
| union-find | `Vec<Cell<usize>>`, `find(&self)` compresses | owned array threaded (`uf-bounded`); the same with the walks as `unfold` loops under `div_fuel` (`uf-fuel`) | 46 → 105 / 127 | yes | 1 / 0; 6664 / 130 | `find(&self) -> usize` becomes `A * i32 => A * i32` |
| memo cache | `RefCell<HashMap>` + `Cell` misses, `get(&self)` | table threaded (`memo-owned`); table in a cell lent `mut` (`memo-mut`) | 25 → 75 / 85 | yes | 1 / 0; 2 / 0 | `&self` becomes owned in, owned out, or `mut 'a M` |
| counter / `Fn` callback | `Cell` captured by an `&dyn Fn` closure | count threaded through the callback (`counter-thread`); `mut 'a i32` passed to the callback (`counter-mut`) | 20 → 15 / 29 | yes | 0 / 0; 1 / 0 | callback `Fn(i32)->i32` becomes `!(i32*i32 => i32*i32)` or `!(mut 'a i32 * i32 => mut 'a i32 * i32)` |
| lazy config | `static LazyLock<Config>` | once-cell as a value `(C + 1) * inits`, threaded (`lazy`) | 22 → 34 | yes | 0 / 0 | readers take and return `L`; after the first read, `C` is a plain parameter |
| tree, parent pointers | `Rc<Node>`, `RefCell<Weak<Node>>` parent, `RefCell<Vec<Rc>>` children | arena: one array of `(parent, value)`, ids are indices (`tree-arena`) | 34 → 69 | yes | 1 / 0 | `&Rc<Node>` becomes `Ar * Id`; no `Weak`, no refcount |
| recording mock | Book's `MockMessenger { RefCell<Vec> }`, `send(&self)` | `set_value[M]` generic in the messenger's state, `send : !(M * i32 => M)`; the mock conses (`mock-cap`) | 37 → 45 | yes | 26 / 0 | `&dyn Messenger` becomes the state plus its `send`; the mock is pure |
| event emitter | `Vec<Box<dyn Fn(&Event)>>` sharing `Rc<RefCell<Stats>>` | handlers `!(St * Ev => St)`; registry folded to one handler; caller threads `St` (`emitter`) | 41 → 47 | yes | 40 / 35 | handlers return the state instead of capturing it |
| BFS | nodes with `visited: Cell<bool>`, `dist: Cell<i32>`, over `&Graph` | graph, dist and queue arrays owned and threaded (`bfs`) | 38 → 116 | yes | 3 / 0 | `bfs(&Graph)` becomes a function of the owned arrays |

About 15 lines of each `bc` file are array `get`/`set` and the `twice` combinator. There is no
standard library yet to import them from (§4). The loops are fixed compositions of a step
(`twice`), as in the corpus, which bounds each loop by the program's size. `uf-fuel` writes the
same loops as `unfold` loops. It runs them under `div_fuel` because a div function whose result
holds an array cannot end in a total expression: the sugar's generated `<return inl v, return ()>`
leaves `v` undropped in a value (Frontend/README, checker incompleteness 8). Its 6664 allocations
are `div_fuel` converting the `i32` fuel to a unary numeral on every call; the union-find
itself allocates the one array.

What is lost and what is gained, per program:

- **union-find, memo, BFS.**
  - *Gained:* `find` is a function of the table, so the compression is visible in the type,
    and no other holder of the structure can observe a half-updated table.
  - *Lost:* concurrent readers of one structure (`same(&self)` from two places at once).
    Callers must be sequenced.
- **counter.**
  - *Gained:* the count is in the callback's type, so a callback that counts cannot be passed
    where an uncounted `!(i32 => i32)` is expected. The callback stays pure (`counter-thread`)
    or names its one borrowed cell (`counter-mut`).
  - *Lost:* passing a counting closure to an API written for plain callbacks without changing
    that API.
- **lazy.**
  - *Gained:* initialization order is explicit and is a value.
  - *Lost:* reaching the configuration from a function that was not given it. There are no
    globals (decision 30).
- **tree.**
  - *Gained:* no refcounts, no `Weak` upgrade failures, and one allocation, against one `Rc` box per
    node plus the children vectors in `rs/tree.rs`.
  - *Lost:* removing a node leaves a stale index (Matsakis's caveat); a generational index
    would catch it.
- **mock.**
  - *Gained:* the mock is a pure function and the test reads its log as a value. The same
    `set_value` runs in production at `M = Out`.
  - *Lost:* every caller between the test and `set_value` threads `M`. A State handler would
    remove that (`sketches/state-handler.bc`).
- **emitter.**
  - *Gained:* handlers are pure and composable, and the stats cannot be mutated behind the
    emitter's back.
  - *Lost:* handlers cannot each own a private piece of state that outlives a call, and there
    is no emitter the host can call back into later with state it does not hold (category 6's
    GTK and JS cases). The 35 dispatched calls are 7 per event: the 3 handlers and the 4 layers
    of the composed registry. Rust's version makes 15 `dyn` calls.

## 3. The options, and which category each covers

The alternatives are:

- **A. `&mut` / owned threading.** Built.
- **B. Capability parameter.** Built (SPEC §11).
- **C. Arena with typed indices over arrays.** Built (SPEC §9), but hand-rolled here.
- **D. State through a fold or a loop.** Built.
- **E. State handler.** #18, not built (`sketches/state-handler.bc`).
- **F. Opaque-handle `Cell`.** A std-lib type implemented in `unsafe` (#79, not built): the
  contents live in a runtime store outside the model heap, `get`/`set`/`replace`/`take` take
  `imm 'a (cell T)`, and it is listed by `bcc trusted` under `unsafe`
  (`sketches/cell-handle.bc`).
- **G. Opaque-handle `RefCell`.** F plus a borrow flag. `with_borrow_mut` takes the contents out,
  lends them from a fresh model cell as an ordinary `Mut` borrow, and puts them back. A second
  borrow takes the error branch (`sketches/refcell-handle.bc`).
- **H. `unsafe` write through an `Imm` borrow.** Its contract is false; see below.

F and G need no model change. An `Imm` borrow freezes the model cell holding the handle, and
`Imm̲` of an opaque type is `Unk`, so the model heap stays deeply immutable and `imm_call_keeps`
still holds. What they cost:

- the store and the flag are trusted runtime code, with a contract stated on #79;
- a function that reaches a handle is not pure, and this shows in its type, because the handle
  is effectively a capability;
- contents start as plain data. Resource-holding contents need the destructor to hand them
  back, or leak freedom stops covering the store.

**H is closed.** #79 reads the contract as the declared signature. A body that stores through
`imm 'a i32` contradicts `imm_call_keeps`: every semantically typed callback given `imm 'a A`
leaves that cell unchanged on the run `wpTS` exhibits and on every run that does not allocate.
`proved` is therefore impossible, and `assumed` makes the end-to-end theorem vacuous for that
program (`sketches/unsafe-imm-cell.bc`).

| category (sample) | today (A–D) | E handler | F `Cell` handle | G `RefCell` handle |
|---|---|---|---|---|
| 1 cache/memo (11) | **well**: `memo-*`; `&self` becomes `&mut` | removes the plumbing | plain keys and values: yes, and `&self` stays `imm` | any `T`, re-entrancy caught as `inr` |
| 2 counters (7) | **well**: `counter-*` | yes | yes | — |
| 3 lazy (5) | **well** as a value (`lazy`); a static: no | yes | `OnceCell`: yes; `LazyLock` static: no | — |
| 4 shared graphs (4) | **well** as an arena (`tree-arena`); `Rc` sharing: **no** | no | no: the handle is linear | no: exclusive borrows only, and the handle is linear |
| 5 mocks (11) | **awkward**: parameter threaded (`mock-cap`) | **well** | plain log: yes | yes |
| 6 host callbacks (8) | pure handlers over threaded state: **awkward** (`emitter`); state captured by `'static` closures: **no** | the loop owns the state (Elm-style) | no: `!` closures cannot capture `imm` (§10) | no, same reason |
| 7 `Fn`/`FnMut` (1) | **well**: the core has one callback type; pass the state | — | does not help: the closure still cannot capture the handle | — |
| 8 graph algorithms (1) | **well**: `bfs`, `uf-*` | — | yes | yes |
| 9a ambient thread-local (10) | **no, by design** (decision 30): parameters | a handler per context | no global handles | — |
| 9b accumulators (6) | **awkward**: `&mut` sink threaded | **well** (Writer) | plain: yes | yes |
| 9c markers (3) | **awkward**: set threaded | yes | yes | — |
| 9d arena annotations (6) | **well**: side table indexed by node id (`tree-arena`'s pattern) | — | yes | — |
| 9e FFI, re-entrancy (4) | out of scope: `extern` | — | — | flag = re-entrancy guard |

Over the 77 non-plumbing sample sites:

- **Well today: 31 sites** (categories 1, 2, 3, 7, 8, 9d), always with an API change from
  `&self` to `&mut` or to an explicit argument.
- **Awkward: 20 sites** (5, 9b, 9c). They work, with the state threaded through every
  intermediate signature.
- **Split: 12 sites** (4 and 6). The arena version of a graph and pure handlers over threaded
  state work. `Rc` shared ownership and `'static` host callbacks capturing state do not. The
  sample was not re-read to divide these 12 sites between the two halves.
- **Excluded: 14 sites.** 10 are ambient thread-local state (9a), excluded by decision 30 rather
  than missing. 4 are FFI (9e), which belongs to `extern`.

**Which uses the opaque `RefCell` (G) covers.**

- **Mocks** (the Book's `RefCell<Vec>`): covered, and plain logs are also covered by F.
- **Caches of resource-holding values:** covered, since exclusive borrows work for any `T`.
- **Registries owned by one value**, such as an emitter holding its handler list: covered.
- **Anything that needs several holders of the same cell:** not covered. That means graphs with
  shared owners, observers that each keep the subject, and GUI callbacks that capture
  `Rc<RefCell<State>>`. In all of these the missing piece is shared ownership plus capture by a
  reusable closure, not mutation through a shared borrow.
- **Simultaneous shared borrows of resource-holding contents**, e.g. two `borrow()`s of a
  `RefCell<Vec<Box<_>>>` live at once. Needed where Rust iterates a registry while a handler
  reads it. G's simple version allows one borrow at a time.

## 4. Recommendation

**Do not add a shared-cell resource kind to the model.** The evidence:

- **The textbook case is small.** Shared-ownership graphs, the case that would need a new kind,
  are 4/90 of sampled sites. Rust's own guides answer it with arenas, and `tree-arena.bc` shows
  the arena works here today with one allocation.
- **A model kind would not fix what F and G cannot reach.** Every category that is
  inexpressible today stays inexpressible under F and G, and the reason is not mutation. It is
  shared ownership (`Rc`) and closures capturing non-persistent values. A model kind whose `Imm`
  clause permits writes would add the price (re-proving `↭`'s `imm` clause, 6.131 and every
  frame result with an exception) without adding either of those.

**In order of evidence per cost:**

1. **Arena and array helpers in a standard library.** Every `bc` program re-implements `get`,
   `set` and a bounded loop, which is roughly 15 of its lines. The categories that are well
   handled today (31/77) are handled by arrays and threading. What makes the `bc` versions two
   to three times longer than the Rust is the missing library, not the missing `Cell`. A typed
   arena (`Arena T`, `Id T`, generational if removal matters) over §9 arrays needs no kernel
   change.
2. **State and Writer handlers (#18)** for the awkward group: mocks, accumulators, markers and
   event state (20/77, plus the pure half of category 6). They remove the threading through intermediate signatures while keeping
   the effect in the type, which is what `sketches/state-handler.bc` shows for the Book's mock.
3. **The opaque-handle `Cell`/`RefCell` (F, G) as a later `unsafe` std-lib type (#79)**, only
   when a program needs mutation while aliased, meaning several simultaneous `imm` readers of
   one handle, which `&mut` cannot give. It costs no model change and has an honest contract,
   but by itself it recovers little. The survey's big `&self` categories (caches, counters) are
   already expressible with `&mut`. The one thing F and G add is keeping `&self` signatures. And
   because a `!` closure cannot capture a borrow of the handle, they do not reach the callback
   categories where Rust needs them most.
4. **Leave shared ownership (`Rc`) and host callbacks capturing state as the open gap.** These
   are part of the 12 split sites, plus the thread-local cases excluded by design. Covering them needs an
   explicit, opt-in reference-counted resource and a closure former that may capture it. That
   is a separate design question from interior mutability, and decision 3 and the no-GC policy
   bear on it.
