# Unsafe: asserted, not proved

Design document. Status words: EXISTS (in the code), DESIGNED (written down, not built),
DECIDED (a recorded user decision), OPEN (a question for the user). What this document proposes
is marked PROPOSED; none of it is decided.

## 0. Purpose

Sometimes a program or a language feature is believed sound but not proved. This document
gives one mechanism for going ahead anyway, so that each new feature that needs it does not
decide the question again. The mechanism must keep four properties:

- **Programs that assert nothing keep their guarantees unconditionally.** Their fundamental
  property, adequacy and borrow guarantees carry no hypothesis.
- **Every assertion is named and enumerable.** It is a hypothesis of the end-to-end theorem.
  The checker reports which assertions a program relies on, and the trusted base is generated,
  never declared by hand.
- **Every assertion can be falsified by a run, and has a falsifier.**
- **Proving stays the default.** An assertion is an escape hatch for a gap that is proof-only:
  the program behaves correctly and the property is believed (DECIDED, 2026-10-14).

## 2. The principle

PROPOSED. **An assertion is the logical relation at one site: a term the program contains, at
the judgment the checker expected there.** Laws, rules and contracts are where sites come from,
and they are what a proof discharges, but the hypothesis of a program's theorem is always a
finite list of sites.

### 2.1 Sites

A site is `(Δ, Γ, e, j)`, and the assertion is `SemJ Δ Γ e j`. A site is either **written** or
**licensed**:

- **Written.** An extern (a variable whose implementation is supplied), a compiled unsafe body
  (decision 27, #79), or `trust e`. The programmer put it there.
- **Licensed.** A language rule the checker uses but the kernel does not prove. R1 and R2 are
  the first two. The programmer writes nothing; the checker emits the site because the rule's
  premises hold there.

**The theorem.** The checker returns a derivation of `TDerives`, which is `CDerives` with one
rule added,

        (Δ, Γ, e, j) ∈ 𝒯
    ─────────────────────
      TDerives Δ Γ e j

where `𝒯` is the program's table of sites. Then:

- `fundamental_trusted (H : ∀ s ∈ 𝒯, SemJ s) : TDerives Δ Γ e j → SemJ Δ Γ e j`;
- `adequacy_trusted`, stated the same way;
- `TDerives.ofC`: every `CDerives` derivation is a `TDerives` one with `𝒯 = ∅`.

A program with `𝒯 = ∅` is a `CDerives` program and keeps `fundamentalC` and `adequacyD` with
no hypothesis. `fundamental_sites` (`experiments/Unsafe/Unsafe/Compose.lean`) checks this shape
at an abstract rule set. An extern stays a context slot: the site whose term is a variable.

### 2.2 Licences

A licensed rule has two parts, which the current `PinLaw` keeps together:

- **The licence**: the rule's premises, which the checker decides (for R1: `Row.ResumeO`, the
  closedness of the body, `NoThunkT`, the body's derivation in `CDerivesP`). They decide which
  sites the checker may emit without a `trust`.
- **The schema**: the rule's compatibility lemma at its premises (`PinStop`). It implies every
  site the licence emits (`pinSite_of_pinLaw`, `experiments/Unsafe/Unsafe/PinSite.lean`, which
  elaborates against `Core/PinLaw.lean`). It is the evidence for the sites, the target a proof
  aims at, and, once proved, the reason they all leave the trusted base at once.

The proposal is that the theorems take the sites as their hypothesis and the schema stays a
schema. §4 gives the reasons and the alternatives.

### 2.3 Outside the model

Some trusted facts are not about the logical relation at all: that the compiled program behaves
as the interpreter does, that the allocator meets its written specification, that a host
implementation agrees with its extern's model (SPEC §11 *Assurance*, `Backend/README.md`). They
relate two semantics, so no site expresses them. They are a separate category of the trusted
base (§8). The facts EXIST and are trusted today; naming them as a category is PROPOSED.

### 2.4 The strength order

Four forms of one claim, strongest first. Each implies the next
(`experiments/Unsafe/Unsafe/Compose.lean`):

| form | statement, for a law rule `L` over a base `R` | in `Compose.lean` |
|---|---|---|
| semantic law | `L`'s compatibility lemma at every related premise | `Closed L Sem` |
| law over a larger judgment | at premises derived in `R + r + L` | `LawOver (R.add r) L Sem` |
| law over the judgment | at premises derived in `R + L` (`PinLaw` today) | `LawOver R L Sem` |
| sites | at the premises of each site the program uses | `∀ a, T a → Sem a` |

`lawOver_of_closed` and `lawOver_strengthens` give the first two steps, and `sites_of_law` the
last. The first step is strict: `junk_refutes_semantic_law` exhibits a law that holds over the
judgment and fails at a related premise no derivation builds. The second is strict too:
`sound_rule_breaks_law` adds to the base a rule that has its own compatibility lemma, and the
law that held before is then false.

### 2.5 Inside trusted code

From decision 27 and #79 §2, unchanged:

- **A trusted body is shape-checked, not borrow-checked.** Lifetimes, modes and linearity are
  erased; shapes are kept (`i32`, sums, products, arrays, pointer to a shape, closures). A
  shape-typed body never gets stuck at a non-memory operation. DESIGNED.
- **Raw memory goes only through the `RawMem` capability.** Its operations are where a trusted
  body can fail, and the interpreter checks them dynamically. A capability is passed, never
  ambient (decision 30), so a `trust` site can use raw memory only if it is given `RawMem`.
  DESIGNED.
- **No raw pointer leaves a trusted body.** The boundary's type is a safe type, and the contract
  is the relation at that type. DESIGNED.

### 2.6 Rules for an assertion's statement

These apply to every site and every schema.

1. **A hypothesis, never an axiom.** A `def … : Prop` or `structure … : Prop` taken as an
   argument. `#print axioms` stays within `[propext, Classical.choice, Quot.sound]`.
2. **No quantifier over code except over derivations.** A site fixes its term. A schema
   quantifies over code only through derivations (`PinLaw`'s form), never over semantically
   related code. A site still quantifies over related substitutions for its context: that is
   §5.
3. **The claim itself, nothing smaller.** Assert the site's relation, or the rule's
   compatibility lemma, never an intermediate step of a proof route. A route's step can be
   false where the claim is true: `PinStop` was first stated as the borrower's half of R1, and
   that half's cancel clause returned the owner before the borrower's finalisers ran.
4. **Fixed text.** `bcc trusted` prints every assertion's statement with a digest, and a change
   to it is a reviewed diff (§7.6). Nothing changes what a program assumes without a line of its
   trusted report changing.
5. **Non-vacuous.** At least one program that relies on it is checked and runs; for a licence,
   that program is one `CDerives` refuses.
6. **Falsifiable by a run, with a falsifier** (§9).
7. **Proof is the default.** `trust` is free for programmers to use, and the trusted base
   records it. A licence is a language rule, raised with the user case by case.

## 3. The questions

§4 to §9 take the six questions in turn. Each gives options with their costs, then a
recommendation. Every recommendation is PROPOSED; the user decides. §13 collects them.

## 4. Q1: what a licence's assertion ranges over, and how it composes

**The problem.** `PinStop`'s premise is the body's `CDerivesP` derivation, and `CDerivesP` is
generated from `CDerives`. So every rule added to either judgment widens the set of bodies
`PinStop` covers, with no change to its text: `nilDead` and BOXED-κ's `effHandleVB` are in its
domain though its text names neither. `lawOver_strengthens` states this monotonicity, and
`sound_rule_breaks_law` shows why it matters: the new rule's own compatibility lemma, the
obligation every `CDerives` rule already discharges, does not keep the law true. Each rule
addition is a new assertion.

### Options

**A. Accept, and version the schema.** `PinLaw` keeps its form. `gen-pin.py` emits the list of
rules `CDerivesP` contains, and the list is part of the schema's statement in SPEC and in
`bcc trusted`. A rule addition bumps the version, with a spec line ("`PinLaw` now covers `X`"),
a user sign-off and an adversarial program that uses `X` inside a relaxed lend.
- *At the next rule addition:* no proof; one program, one line, one decision.
- *Cost:* the assertion still grows with every rule, now visibly. A refutation at any version
  makes the theorems vacuous for every relaxed program at once.

**B. Stratify over a fixed base, with a per-rule interaction obligation.** `lendR`'s premise is
a derivation in a frozen `CDerivesP₀`. A new rule may appear inside a relaxed body only after
its interaction obligation is met, and the checker refuses it there until then.
- *What the obligation is:* by `sound_rule_breaks_law` it cannot be the rule's compatibility
  lemma at `SemJ`. It is either an opt-in version bump (A, per rule) or a proof at an invariant
  (C). So B adds a checker filter to A or C; it is not a third kind of obligation.
- *At the next rule addition:* the generator emits two judgments; the checker carries a
  per-rule admission flag; a program using the new rule inside a borrow crossed by `await` is
  refused until the rule is admitted.
- *Cost:* the base does not stay frozen. Core is changeable, and a generalization lands with
  the deletion of the rules it replaces (decision 20), so existing rules change and the snapshot
  is re-taken each time, which is A again.

**C. State the schema over an invariant.** `PinLaw` becomes `Closed L I` for a relation `I`
below `SemJ`, and every rule of the base must be closed under `I` (`fundamental_inv`). The
schema's text names `I`, not a rule set; a rule addition costs that rule's compatibility lemma
at `I`.
- *Which `I`:* `I = SemJ` is the semantic law, refutable at junk (`junk_refutes_semantic_law`
  in the abstract; at the `U` clause, `core_not_relend_kU` on `law2-typed-world`). `I` = the
  extended judgment itself is option A. A useful `I` lies between them: a reading that sees what
  typed code builds, such as Law 2's re-lendable reading (`pj_fundamental`: 91 cases, 59 proved,
  6 at part of their instances, 26 not derived), GhostEnd's `vRL`, or a typed world
  (`experiments/CBPVWorld`).
- *At the next rule addition:* one compatibility lemma at `I`, beside the one at `SemJ`.
- *Cost:* a second relation maintained beside `SemJ` for every rule, unless `I` replaces `SemJ`
  as the kernel's relation, which is a model change (tier-2 problem D's second option). And
  asserting `Closed L I` asserts a proof route's step, against rule 3 of §2.6.

**D. Assert per site; keep the schema as a schema.** The hypothesis of `fundamental_trusted` and
`adequacy_trusted` is the relation at each R1 or R2 site the checker emitted, with its body and
finaliser fixed (`PinSite` in `experiments/Unsafe/Unsafe/PinSite.lean`). `PinLaw` keeps its
form and gains one theorem, `pinSite_of_pinLaw`; the checker keeps building each body's
`CDerivesP` derivation as the licence's evidence.
- *At the next rule addition:* no existing hypothesis changes (`fundamental_sites_add`: the
  sites' hypothesis is passed unchanged, and the new rule brings only its own compatibility
  lemma at `SemJ`). A program that uses the new rule inside a relaxed lend gets a new site,
  which shows in its trusted report and is tested by that program's runs. The schema's version
  (A's bookkeeping) still moves, as a record of what the evidence covers.
- *Cost:* the trusted base is per program, and longer: it grows with the number of relaxed
  lends. One proof of the schema still discharges them all. The theorems need `TDerives`
  (§2.1), which `trust` needs anyway. The wording of #52's decision (SPEC §29 *Motivation*),
  "the one assertion needed for it is a named hypothesis of the theorems", becomes "one schema,
  whose instances are the hypotheses".
- *What it does not remove:* a site still quantifies over related substitutions for its
  context, `r : Ref T`, so junk at a higher-order `T` can still make one false (§5). `PinStop`
  has the same quantifier, so this is no worse. On `law2-typed-world`, `semD_relend_fov`
  (DenseCarrier) shows that a fixed term the relation relates re-lends whenever its captured
  context does, and always at a first-order context: with the body fixed, the remaining
  exposure is the context.

**E. The law, restricted to the rules a program uses.** The theorem takes `LawOver R_p L Sem`,
where `R_p` is the set of rules the program's relaxed bodies use. By monotonicity it is weaker
than `PinLaw`, and a rule no existing program uses changes no existing hypothesis.
- *At the next rule addition:* nothing for existing programs; a program that uses the rule
  relies on a larger `R_p`.
- *Cost:* `CDerivesP` indexed by a rule subset, or a computable record of the rules a derivation
  uses (`CDerivesP` is a `Prop`, so the checker would carry the set, as it carries `pins`). It
  keeps a quantifier over every body derivable from `R_p`, so for the same program it is
  stronger than D.

### Cost at the next rule addition

| option | proof | per-rule work | existing programs' hypotheses | reach of one refutation |
|---|---|---|---|---|
| A | none | a program, a line, a decision | grow | every relaxed program |
| B | as A or C | as A or C, plus a filter | fixed until admitted | as A or C |
| C | a lemma at `I` | the lemma | fixed | every relaxed program |
| D | none | none required; a program recommended | fixed | the falsified site's program; the schema's evidence |
| E | none | none | fixed | the programs using that rule set |

### Recommendation

PROPOSED: **D, with A's bookkeeping for the schema, and C as the route that retires it.**

- D is the only option under which adding a rule changes no existing hypothesis and costs no
  proof, and each hypothesis is exactly what its program's runs test.
- A's census (the rules `CDerivesP` contains, printed with the schema) keeps the evidence
  honest: the adversarial list should exercise the rules the schema covers.
- C is how the sites stop being assertions. When an invariant `I` exists and the base is closed
  under it, `PinLaw` is proved, and every site leaves the trusted base with no change to any
  program.

## 5. Q2: a site's context, and junk (OQ-8)

**The problem.** `SemJ Δ Γ e j` asks `e` to behave on every related substitution for `Γ` and at
every world, including related values no program builds. A site that is safe on every value a
program can build, yet misbehaves on such a value, is a false hypothesis. The theorem is then
vacuous for that program while every run is fine, so no falsifier can detect it: the risk is
vacuity, not a run that goes wrong. Every junk witness so far is higher-order:
`core_not_relend_kU` is at a `U` type, `coreAllAdjacent` at a lifetime-polymorphic function
(tier-2 problem D).

### Options

- **(a) The full contract.** The relation at the site's judgment, as for externs. Simple, the
  usual meaning of a contract, and what RustBelt asks of a library (§11). It risks vacuity only
  for a site whose context has a higher-order type at a position it uses.
- **(b) Arising substitutions only.** Quantify over the substitutions typed programs build.
  Needs a derivation-indexed invariant, which does not exist (problem D's first option). The
  most precise option.
- **(c) First-order contexts only.** Allow `trust` only where the slots the site uses have no
  `U` and no `∀`. Junk-free as far as is known, since every witness is higher-order. It refuses
  sites that hold a closure, which include most callbacks. Lifting the site into a closed
  function does not help: the lifted constant's contract is the relation at a function type
  whose arguments are the same context.
- **(d) The whole program.** Assert the closed program's adequacy, with the site as its
  provenance. No junk, and exactly what a run tests; but it trusts the whole program, and
  nothing about the rest of it is checked.

### Recommendation

PROPOSED: **(a) as the contract, with (c) as a report, not a restriction; (b) when a relation
that sees what typed code builds lands.** `bcc trusted` marks a site whose used context has a
`U` or a lifetime `∀` at a position the site reads as *higher-order context*: these are the
sites whose hypothesis could be vacuous. If the kernel's relation changes (problem D's second
option), each site is re-read at the new relation, and no source changes.

## 6. Q3: decision 27 and `trust e` at subterm granularity (OQ-3)

**The problem.** Decision 27 says there are no unsafe blocks inside safe code, and `trust e` is
one. Its reason is that raw pointers must not flow into safe code, so that provenance never
needs tracking.

### Options

- **(a) Amend the wording.** A trusted boundary may sit at any subterm, provided its type is a
  safe type; inside it the shape check applies; no raw pointer crosses it. The reason survives:
  the boundary is still a safe type, and `RawMem` is a capability that must be passed in.
- **(b) Keep the wording.** A trusted subterm must be lifted by hand into a named `unsafe fn`
  whose arguments are its context. The same contract (§5 (c)), more ceremony, and against the
  user's "the checker reports, and the user trusts" (#79).
- **(c) Lift in the elaborator.** `trust e` elaborates to a closed trusted constant applied to
  the site's free variables, generalized over the lifetimes they mention, so decision 27's text
  holds of Core verbatim. It costs a lifting pass and a lemma that the constant's contract is
  the site's relation. `TDerives`' site rule already handles open sites, so it buys only
  uniformity.

### Recommendation

PROPOSED: **(a).** The amendment states what decision 27 protects. (c) stays available if a
single closed form in Core is wanted later.

## 7. Q4: the remaining questions

### 7.1 Who may add a licence (OQ-2)

- **The language only:** a SPEC entry and a user decision, like any kernel rule.
- **Libraries may declare asserted rules:** the checker becomes extensible by rule
  declarations, and the trusted base includes rules no spec entry reviewed, which widen checking
  for every importer.
- **Libraries may declare derived rules only:** rules proved admissible, so no new assertion;
  an asserted rule stays the language's.

PROPOSED: **the language only, for now.** Under §4's D, a library rule would only license
sites, each reported, so the question becomes how far to extend the checker rather than a
soundness question. Revisit when a library needs a rule.

### 7.2 The evidence ladder (OQ-4)

- **One ladder for every site.**
- **One ladder per provenance** (written, licensed).
- **Unordered evidence tags** (tested, dynamically checked, partially proved, proved).

PROPOSED: **one ladder, per site**, since every assertion is a site. The rungs, read per site:
(1) assumed; (2) interpreter-checked: a falsifier run reached the site (for R1, a suspension
crossed that site's lend); (3) property-tested: adversarial inputs or schedules reached it;
(4) typed low-level: a shape-checked body (written sites only); (5) boundary-checked: the
dynamic checks run at the site in compiled code; (6) semi-automatically verified; (7) proved, at
the site or by a proof of its schema. A partial proof of a schema (Law 2's 59 of 91 cases) is a
note in the report, not a rung: the one case not derived can be the false one.

### 7.3 Sites in generic code (OQ-5)

A `trust` inside a function the elaborator copies per row or type (§14 specialization) is one
site per copy: each copy is a different term at a different judgment.

- **Report each copy.**
- **Report the source site once.**
- **One row per source site, with its copies under it.**

PROPOSED: **one row per source site, listing its copies**; the hypotheses stay per copy. The
report marks the copies no falsifier run reached.

### 7.4 Effects across a boundary, and nested sites (OQ-6)

A site's judgment includes its row and its cancel rows, so its contract covers the operations it
performs and the cancellation of a continuation captured inside it. What needs a rule is
nesting:

- **The outermost site is the hypothesis.** A site is a leaf of the `TDerives` derivation, so a
  site inside another site's term is not a separate hypothesis.
- **The report lists both.** The outer site's credibility rests on the inner one.
- **A `trust` inside a relaxed lend is outside the schema.** `pinSite_of_pinLaw` needs the
  body's `CDerivesP` derivation, and a body with a trusted leaf has none. For `PinLaw` to cover
  it, `PinStop` would have to range over bodies with trusted leaves, that is, over leaves known
  only to be related, which is junk-exposed at higher-order contexts. At a first-order leaf
  context `semD_relend_fov` suggests it would hold; this is not checked.

PROPOSED: **the checker accepts the nesting; the outer site is the hypothesis, reported as not
covered by its schema, at the lower of the two levels.**

### 7.5 On falsification (OQ-7)

- **Block the gate.**
- **Report only.**
- **Quarantine:** the program moves to `corpus/pending` with the falsifier's output.

PROPOSED: **block, for every kind of site.** A written site that fails is a bug report: the
program or the site's type is wrong, and it is fixed, or quarantined in the same change. A
licensed site that fails refutes the schema: the licence is restricted (its premises narrowed so
that the falsifying program is rejected, and the program added to `corpus/reject`) or the rule
is removed, and the schema's version moves. Under §4's D only the falsified site's own theorem
becomes vacuous, but every site the same schema licenses drops to *assumed* until the
restriction lands, since the evidence they share has failed.

### 7.6 Ascription (OQ-1)

- **Always required:** `trust (e : A)`.
- **Required only where the checker cannot supply the judgment** (synthesis mode, or the
  subterm is why inference failed).
- **Never:** the checker always prints the judgment it used.

PROPOSED: **required only where the checker cannot supply the judgment.** When it is not
written, the judgment can change silently when the surrounding code changes. So `bcc trusted`
prints each site's judgment and a digest, and every corpus program with a site has a `.trusted`
golden: a changed assertion is a diff in review. The same golden serves §4: it is how a change
to a licensed site's body becomes visible.

## 8. Q5: is the two-kind split right?

**Can a licence be a constant at a type?** As a constant, R1 is `withborR : Ref T ⊸
U(∀'x. Mut 'x T ⊸ F_Σ ([@x] B)) ⊸ F_Σ (Ref T ⊗ B)`, and its contract quantifies over every
related callback. That is the semantic law (`Closed L Sem`), and the callback's type is a `U`
type, where the known junk is. So no: a constant brings back the junk-refutable quantifier,
unless the kernel's relation changes so that a `U` value is related only when typed code could
have built it. Then a licence becomes a closed written site, an `unsafe` constant with its
contract.

**Can a licence be per site?** Yes, without that quantifier, because the body is fixed (§4's D).
This is the proposal: one kind of assertion, the site, with two provenances, written and
licensed. Kind R of the earlier draft becomes a rule of the checker, not a kind of hypothesis.

**Is there a third kind?**

- **Model facts:** a claim about a type's interpretation that generic safe code relies on
  (Rust's `unsafe impl Send`, `Sync`; here, for example, a claim that a type is persistent so
  that the copy rule applies). By the same principle such a claim would be licensed per use
  site, not stated over every related value. None exists: opaque types' models are definitions,
  not assertions.
- **Lowering and runtime facts** (§2.3): the backend, the allocator, host implementations. They
  are not hypotheses of the model's theorems. They exist today, and the differential runs of
  every stage against the goldens, already in the gate, are their falsifier.

PROPOSED: **one kind of hypothesis, the site, with two provenances; lowering and runtime facts
as a separate category of the trusted base, outside the model.**

## 9. Q6: the falsifier as a standard part

### What every assertion ships with

PROPOSED:

1. **Its statement,** generated, with a digest (§2.6 rule 4).
2. **A relying program** that checks and runs; for a licence, one `CDerives` refuses.
3. **Evidence that the site was reached.** A falsifier run that never reached the site is not
   evidence. `--stats` counts the suspensions that crossed any lend; it needs a count per site
   (V4).
4. **The observations that refute it:** a stuck run, a leak, an answer outside the type, a tag
   error, a `RawMem` check failure. A site may name more.
5. **For a licence, an adversarial list:** for each premise, a rejected program that violates
   only that premise; and accepted programs for each way the rule meets the others (nesting,
   cancellation, closures over the view, finalisers), as `docs/async-capabilities.md` §6.2 has
   for R1.
6. **A negative test for each new check:** an untyped term the check must catch, as
   `bcc kernel negatives` has for the tag check.

Every check must follow from a property the relation guarantees for typed programs: a check
that fails on a program the relation accepts is a bug in the falsifier, not a refutation. The
tag check has one known blind spot: `withbor1` and `withbor2` erase alike, so a write through
an `imm` view lent by `withbor1` is not detected.

### In the gate

- **(a) The whole falsifier in `make gate`** (about 20 minutes).
- **(b) Relying programs in `make gate`, the whole corpus in `make gate-full`.** A relying
  program is one whose assurance is not unconditional. The whole corpus also runs when
  `Backend/Falsify.lean`, the erasure, a licence's checker code or `gen-pin.py`'s output
  changes.
- **(c) Outside the gate,** on demand or nightly.

PROPOSED: **(b).** The relying programs are few: the seven R1 corpus programs run four ways in
about three seconds (`scripts/falsify.sh corpus/async-r1-*.bc`). The whole corpus belongs with
the other long run. `make gate-fast` runs the falsifier on the relying programs it touches.

## 10. Reporting

- **`bcc check`** prints one line: `assurance: unconditional`, or the sites, e.g.
  `assurance: trust 12:5; R1 23:5`. EXISTS for R1 and R2, as `assurance: PinLaw (R1 at …)`.
- **`bcc trusted`** generates the trusted base in three groups (#79's categories, extended):
  written sites (externs, unsafe bodies, `trust`); licensed sites, each with its schema and the
  schema's rule census and version; and facts outside the model (backend, allocator, host
  implementations). Each site has its judgment, digest, level, the copies it stands for, the
  sites nested in it, and whether its used context is higher-order. EXISTS for externs and, in
  part, for licensed sites; the rest is PROPOSED.
- **No ceremony in source.** No assurance clauses and no theorem names; a licensed site needs
  no marker. Evidence is attached out of band and raises the level (#79).
- **Migration.** A proved site leaves the trusted base, and neither its type nor its callers
  change. A proved schema moves its rule into `CDerives`, and every site it licensed leaves the
  base at once.

## 11. Prior art

**RustBelt** (Jung, Jourdan, Krebbers, Dreyer, POPL 2018). A library's unsafe implementation is
proved to inhabit its semantic type against every semantically typed client: §5's (a), and what
a written site's contract means. Every typing rule is a lemma in one fixed model and none is
asserted, which is §4's C with the model as the invariant. That works because the model's types
are rich enough for the safe-abstraction claim to hold at every related client, which problem D
says our relation is not yet at `U` types.

**Semantic typing as a method** (Timany, Krebbers, Dreyer, Birkedal, *A Logical Approach to Type
Soundness*, JACM 2024). Syntactically typed code may use semantically typed code, and safety
follows from adequacy: `TDerives` with sites. A new rule is justified by proving it in the
model, which is what C asks of each rule.

**RefinedRust** (Gäher, Sammler, Jung, Krebbers, Dreyer, PLDI 2024). Semi-automatic verification
of unsafe Rust against RustBelt-style types: rung 6 of the ladder, and #79's open "bridge" from a
shape-checked body to its contract.

**Iris** (Jung et al., *Iris from the ground up*, JFP 2018). One adequacy theorem with no
hypothesis, and every program-specific fact proved inside the logic; rules are derived, never
added. It supports C, and keeping the base theorems unconditional.

**Rust's `unsafe`** (the Rustonomicon; RFC 2585). An `unsafe` block is an obligation at a
subterm, discharged by its author: the granularity decision 27 refused and `trust e` adopts. Its
soundness boundary is the module, by privacy, not the block, because raw pointers flow within
it; ours is the site's safe type (§6). An `unsafe fn` puts a precondition on its callers, for
which our contracts, being semantic types, have no slot; not proposed now. `unsafe impl Send`
and `Sync` assert a fact about a type's interpretation that safe generic code relies on: §8's
model facts. RFC 2585's `unsafe_op_in_unsafe_fn` lint narrows obligations to explicit sites,
the direction §2 takes.

**F\* and Dafny.** F\*'s `assume val` adds an unchecked declaration and `admit()` closes a goal
unchecked: assumptions are marked in source, not gathered into a generated list. Dafny warns on `assume`, refuses to compile it without
`{:axiom}`, and `dafny audit` generates the list of assumptions (assumes, axioms, bodyless
declarations, externs). That is `bcc trusted`'s model: assumptions are marked, and the list is
computed.

**Liquid Haskell's `assume`.** An asserted refinement signature on a binding whose body is not
checked: a closed written site whose contract is text the programmer wrote. The type is always
written; §7.6 proposes printing it instead when the checker supplies it, with a golden so that a
change is seen.

**Lean.** `axiom` and `sorry` are tracked by dependency, and `#print axioms` computes each
theorem's trusted base: the model for a generated base. Lean also separates logical assumptions
from trust in the compiler (`native_decide` rests on `Lean.ofReduceBool`; `implemented_by`
substitutes code unchecked), which is §2.3's category of facts outside the model.

**Stacked Borrows and Tree Borrows, run by Miri** (Jung, Dang, Kang, Dreyer, POPL 2020;
Villani, Hostert, Dreyer, Jung, PLDI 2025). An operational aliasing model, executed by an
interpreter, finds violations only on executed paths and is far slower than compiled code, so
projects run it on a chosen set in CI: §9's (b), and the reason a pass must show the site was
reached. Tree Borrows changed which programs are violations, so the dynamic model is itself a
choice: ours must reject only what the relation excludes (§9).
